# 学习通课程自动化工作流

> 把「章节测验答题」和「视频进度上报」这两件纯体力活，做成一条可复现、可复用的流水线。
>
> 不是油猴脚本合集，是一个**带状态追踪、能自己发现异常并降级的**小系统。

## 背景

在线课程平台的进度考核有两个特点：**量大**、**机械**。

以实际部署的一门课为例（中国人民公安大学，超星学习通私有部署）：

| 指标 | 数值 |
|---|---|
| 章节数 | 32 |
| 章节测验 | 32 套，约 400 道题 |
| 视频任务点 | 32 个 |
| 视频内容总时长 | 418 分钟 |

两门课加起来是 **64 套测验、850 分钟视频**。这不是学习，是重复劳动。

现有的开源方案（例如本文致谢里的小哀助手）解决的是**单个页面内**的问题：
打开一章，它帮你把这一章的题答完。但真正消耗人的是**跨章节、跨课程的调度**：
32 章要一章一章点进去、有章节已经做过要跳过、中途浏览器崩了要能续、
视频跑完一个要接着跑下一个。

这个项目做的就是这一层。

---

## 实测结果

一次真实部署（同一账号，连续两门课）：

| 课程 | 章节测验 | 视频 | 备注 |
|---|---|---|---|
| 世界文明史 | 32/32 提交 | 32/32 通过 | 一次跑通 |
| 儒学复兴与当代启蒙 | 32/32 提交 | 32/32 通过 | 中途触发限流，自动降速后完成 |

所有「通过」均以**服务端返回的 `isPassed` 字段**为准，而不是脚本日志的自述。
收尾用独立命令逐个复核（`step6_video.py --state`），避免日志滞后造成的假阳性。

单章测验耗时 30–90 秒；850 分钟视频内容在 1.5× 速率下约 9 小时。
**这个下限由服务端的授权机制决定，任何调参都突破不了** —— 详见下文。

## 架构

```
┌─────────────────────────────────────────────────────────┐
│  config.json          学校域名 / API 密钥 / 默认参数      │
└────────────────────────┬────────────────────────────────┘
                         │
              ┌──────────▼──────────┐
              │      lib/cfg.py     │  唯一配置入口
              └──────────┬──────────┘
        ┌────────────────┴────────────────┐
        │                                 │
┌───────▼────────┐              ┌─────────▼──────────┐
│  浏览器通道      │              │    API 通道         │
│  lib/cdp.py    │              │  requests.Session  │
│  原生 CDP 协议   │              │  携带导出的 cookie  │
└───────┬────────┘              └─────────┬──────────┘
        │                                 │
  step0 打开独立浏览器             step4 导出登录态
  step1 读课程 ID                  step5 提取视频参数
  step2 扫章节与任务点              step6 上报视频进度
  step3 注入脚本答题
```

两条通道的取舍是有原因的：

- **答题必须走浏览器。** 题目里有一部分被渲染成自定义字体，DOM 里读到的是乱码，
  需要靠字体映射表还原；答题脚本还依赖页面自身的 JS 环境。用纯 HTTP 复刻代价太高，
  直接注入脚本更稳。
- **刷视频必须走 HTTP。** 视频任务点有 32 个，走浏览器意味着开 32 个标签页、
  每个都要加载播放器。上报接口本身是纯 HTTP 的，直接调用，一路进程能并发跑多个。

## 三个真正难的地方

这部分是这个项目里唯一有技术含量的内容。前面那些章节扫描、批量循环都是体力活。

### 1. 上报请求必须带签名

播放器的进度上报接口：

```
GET /mooc-ans/multimedia/log/a/{cpi}/{dtoken}
```

参数里有一个 `enc` 字段。它是这样算出来的（`step6_video.py: md5enc`）：

```python
raw = f'[{clazz}][{uid}][{jobid}][{objectid}][{playingTime*1000}]' \
      f'[{SALT}][{duration*1000}][0_{duration}]'
enc = md5(raw).hexdigest()
```

把班级号、用户 ID、任务 ID、对象 ID、播放位置（毫秒）、视频总时长（毫秒）
按固定格式拼起来，插一个固定盐值，取 MD5。

**算错一位，服务器返回 200，但这次上报作废** —— 不报错，只是不计入时长。
这个接口的签名规则是从播放器的混淆 JS 里逆出来的。

`dtoken` 也不是常量，每次要单独取：

```
GET /ananas/status/{objectid}?k={fid}&flag=normal
```

### 2. 上报间隔是每门课不同的，且报得勤反而不算

这是踩得最贵的一个坑。

第一版按 30 秒一次上报，想着「勤快点总没坏处」。结果：**位置全部打满，
HTTP 全部 200，一个都不给通过。**

排查时对比了两门课的卡片配置，发现服务端在 `mArg.defaults` 里有个字段：

```json
"reportTimeInterval": 60
```

这门课要求**两次上报间隔不得小于 60 秒**。报得比这更密，增量会被直接丢弃。

把这个值改成 60 秒后，第二个上报周期 `isPassed` 就翻转了。

> 所以 `step5_jobs.py` 会主动解析这个字段写进任务文件，`step6_video.py` 直接用。
> **不再靠猜，也不再靠手动试。**

### 3. 服务端会动态降额，且表现和「参数错误」一模一样

第二门课沿用第一门的参数（60 秒间隔 + 2× 速率 + 3 路并发），结果：
**前 5 个视频通过，后 23 个全部「位置满但不通过」。**

配置完全一样，结果完全不同 —— 说明变的是对方，不是参数。

原因：连续两小时以聚合 6× 的速率消耗课程时长，服务端判定「这不像真人」，
临时收紧了时长授权额度。

**验证方式**（不是猜的）：取一个刚失败的视频，单独用 1.5× 速率重跑 ——
第三个上报周期就通过了。确认是临时降额，不是封号。

处理方式写进了 `step6_video.py` 的主循环：

```python
# 一轮下来一个都没过 → 判定为限速，自动降档
if ok[0] == 0:
    speed = max(1.0, round(speed * 0.7, 2))
    workers = max(1, workers - 1)
```

降到 1.5× / 2 路之后，剩余 23 个全部通过。

## 快速开始

### 环境

Windows 10/11 + Chrome + Python 3.9+

```bash
pip install requests websocket-client
python 环境自检.py
```

### 配置

**① `config.json`** —— 填学校域名和 AI 接口密钥。下面是本项目实际使用的配置：

```json
{
  "school": { "domain": "ppsuc.edu.cn", "name": "中国人民公安大学" },
  "api":    { "key": "sk-...", "base": "https://api.educg.net/v1", "model": "deepseek-v4-flash" },
  "video":  { "speed": 1.5, "gap": 60, "workers": 2 }
}
```

换一所学校只需改 `school` 里的两个字段。`api` 支持任意 OpenAI 兼容接口。

**密钥建议单独放**：新建 `config.local.json`（已在 `.gitignore` 里排除），
只写你要覆盖的字段，两份配置会递归合并、后者优先：

```json
{ "api": { "key": "sk-你的真实密钥" } }
```

这样 `config.json` 可以作为模板一直留在版本库里，不会误提交密钥。

**② 登录** —— 会开一个独立的 Chrome 窗口，和日常浏览器互不影响：

```bash
python step0_open.py
```

在里面登录学习通，点进你的课程。登录态可长期复用。

**③ 登记课程** —— 在那个窗口里点开目标课程的任意一章，然后：

```bash
python step1_discover.py
```

脚本从地址栏反解出 `courseid` / `clazzid` / `cpi` 存下来，不用手抄。

### 日常使用

```bash
python step2_scan.py    <课程号>     # 扫章节，统计习题/视频数量
python step3_quiz.py    <课程号>     # 答题（已完成的自动跳过）
python step4_cookies.py              # 导出登录态给 HTTP 通道用
python step5_jobs.py    <课程号>     # 提取视频参数 + 读服务端要求的上报间隔
python step6_video.py   <课程号>     # 上报视频进度
python step6_video.py   <课程号> --state   # 只复核，不动手
```

详细说明见 **[docs/使用手册.md](docs/使用手册.md)**，
出问题按现象查 **[docs/排查手册.md](docs/排查手册.md)**。

### 两个安全设计

**答题不交白卷。** 上游脚本默认「答不上也提交」。本项目覆盖了它的 `onAllDone` 回调：
**一道题都没答上就中止提交**（`stage: 'no-answer-abort'`），宁可这一章重跑，
也不交一份零分卷 —— 交白卷会直接锁死这一章的重做机会。

**打包脚本会清凭证。** `打包.py` 在生成分发包时会排除 `data/`、`courses.json`，
并把密钥重置为占位符 —— 因为 `data/cookies.json` 里是货真价实的登录态，
直接压缩发出去等于把账号送人。

## 设计取舍

**为什么用原生 CDP，不装 Tampermonkey / Playwright？**

注入脚本本身需要一个宿主。装扩展意味着多一步手动操作和版本漂移；
Playwright 要多装一个浏览器和几十 MB 依赖。CDP 是 Chrome 自带的能力，
开一个端口就行，`lib/cdp.py` 只有 90 行。

**为什么 state 存在本地 JSON，而不是查数据库？**

`data/jobs_<courseid>.json` 里存每个视频的完成状态。看起来简陋，但好处是
**崩溃后直接重跑即可续传**，且随时可以打开文件人工核验。
服务端的真实状态始终是权威 —— 每轮结束都会 `refresh()` 回写一次。

**为什么配置里保留真实学校域名？**

超星在不同学校的私有部署差异不小（域名、接口路径、风控阈值都不同）。
把实际使用的学校写在配置里，是为了让这份代码**可验证、可复现**，
而不是一个含糊的「通用方案」。换成你自己的学校只需改 `config.json` 一行。

## 免责声明

**这是一个技术项目，不是替你完成学业的工具。**

- 本项目只做两件事：调用 AI 回答课后测验、按节奏上报视频进度。
  **它不修改成绩、不介入考试、不伪造任何学习记录之外的数据。**
- **绝对不要在考试中使用。** 考试场景的风险性质与课后练习完全不同，
  且通常有独立的行为审计。
- 使用自动化手段完成课程任务，**可能违反所在院校的学术诚信规定**。
  本仓库作者不对使用者的任何后果负责。
- 仓库内不包含任何账号、密码、cookie 或密钥。`data/` 与 `courses.json`
  已在 `.gitignore` 中排除。

如果课程内容对你确实有价值，**认真看一遍的成本比跑这套脚本低**。
这套东西适合的场景是：内容你已经掌握，只是被时长要求卡住。
