# 技术原理

这份文档记录的是**逆向分析过程与验证方法**，不是使用说明。
想跑起来看 [使用手册](使用手册.md)；出问题看 [排查手册](排查手册.md)。

---

## 0. 为什么分成两条通道

整个系统只有两种与服务器交互的方式，选择依据是**单次操作的成本**。

| | 浏览器通道（CDP） | HTTP 通道（requests） |
|---|---|---|
| 用在哪 | 答题 | 上报视频进度 |
| 为什么 | 题目文字被自定义字体混淆，需要页面 JS 环境还原；且上游答题脚本本身要求 DOM | 上报接口是纯 HTTP，无状态依赖；32 个任务点用浏览器意味着 32 个标签页和 32 个播放器实例 |
| 状态 | 靠浏览器持久化的登录态 | 靠 `data/cookies.json` 里的副本 |

一个反直觉的点：**浏览器通道反而更「轻」**。因为 CDP 是 Chrome 自带的能力，
不需要装扩展、不需要额外的浏览器二进制。`lib/cdp.py` 总共 90 行，
核心就是 WebSocket 上一问一答。

## 1. 视频进度上报：接口解剖

### 1.1 完整请求

```
GET https://{host}/mooc-ans/multimedia/log/a/{cpi}/{dtoken}
```

| 参数 | 来源 | 说明 |
|---|---|---|
| `clazzId` | 课程元数据 | 班级 ID |
| `courseId` | 课程元数据 | 课程 ID |
| `jobid` | 任务点附件字段 | 任务 ID |
| `objectId` | 任务点附件字段 | 媒体对象 ID |
| `otherInfo` | 任务点附件字段 | 需截掉 `&` 之后的附加段 |
| `playingTime` | 本次上报 | **声称**播放到的位置（秒） |
| `duration` | `/ananas/status` | 视频真实时长（秒） |
| `clipTime` | 固定格式 | `0_{duration}` |
| `userId` | cookie 中的 `_uid` | |
| `isdrag` | 见 1.4 | 操作类型 |
| `view` | 固定 | `pc` |
| `dtype` | 固定 | `Video` |
| `rt` | 固定 | `0.9`，播放速率上报值 |
| `enc` | **计算得出** | 签名，见 1.2 |
| `attDurationEnc` | 任务点附件字段 | 有则必须带 |
| `videoFaceCaptureEnc` | 任务点附件字段 | 有则必须带（人脸抓拍课程） |

### 1.2 `enc` 签名

```python
SALT = 'd_yHJ!$pdA~5'

raw = f'[{clazz}][{uid}][{jobid}][{objectid}]' \
      f'[{playingTime * 1000}]'                    \
      f'[{SALT}]'                                  \
      f'[{duration * 1000}]'                       \
      f'[0_{duration}]'

enc = md5(raw.encode()).hexdigest()
```

几个容易踩的细节：

- **时间单位是毫秒。** 传参时 `playingTime` 和 `duration` 是秒，算签名时乘 1000。
- **`0_{duration}` 是字面量拼接**，不是序号。`0` 表示片段起始位置，整段视频就是 `0_总长`。
- **字段顺序不能变**，方括号是分隔符也是内容的一部分。

**签错的表现：HTTP 200，返回体正常，但这次上报不产生任何有效时长。**
这是最难查的一类失败 —— 没有错误码，只有「静默丢弃」。

### 1.3 `dtoken` 不是常量

每次会话都要重新取：

```
GET /ananas/status/{objectid}?k={fid}&flag=normal
```

`fid` 来自 cookie。返回体里的 `dtoken` 有效期有限，所以 `step6_video.py`
在连续上报失败 2 次后会重新拉一次 `status` 换 `dtoken`，而不是硬重试。

### 1.4 `isdrag` 的语义

| 值 | 含义 | 本项目的用法 |
|---|---|---|
| 3 | 正常播放中 | 每个上报周期都用它 |
| 4 | 播放结束 | 到达时长后收尾用 |

`isdrag` 不是「是否拖拽」的布尔值。用错值会被判定为异常操作序列。

## 2. 三个看不见的约束

这三个都不是文档里的东西，全部来自实测对照。

### 2.1 `reportTimeInterval` —— 报得太勤会被丢弃

服务端在卡片页返回的 `mArg.defaults` 里，带一个字段：

```json
"defaults": {
  "reportTimeInterval": 60,
  ...
}
```

含义是：**两次上报的间隔不得小于这个秒数**。比它更密的上报，增量直接作废。

第一版按 30 秒一次上报的实测结果是：

```
位置 364/364（打满）
每次 HTTP 200
isPassed 始终 false
```

把间隔改到 60 秒后，第二个周期就翻转了。**这就是全部原因。**

> `step5_jobs.py` 会遍历所有章节的卡片页，把这个值收集起来取最大值，
> 写进 `data/jobs_<courseid>.json` 的 `interval` 字段。`step6_video.py` 直接读它。
>
> 不要在 `step6_video.py` 里手动 `--gap` 传一个更小的值。

### 2.2 授权比率上限约为 2:1

服务端按「真实流逝时间 × 2」发放可计入的时长额度。
即：每真实过去 60 秒，最多认 120 秒的播放进度。

因此 `step6_video.py` 的步长计算是：

```python
step = int(self.gap * self.speed)     # speed 默认 1.5，即每 60 秒真实时间推进 90 秒
```

`speed` 上限就是 2.0，再高就是纯浪费请求。

**推论：整个流程的耗时下限 = 内容总时长 ÷ 2 + 收尾开销。**
850 分钟内容的理论下限约 7 小时。这是机制决定的，不是实现效率问题。

### 2.3 服务端记的是「累计有效时长」，不是「最后位置」

一个常见误解：以为上报到 364/364 就算完成。实际不是。

服务端为每个任务点维护 `headOffset`（已确认的有效时长）和 `playTime`。
判定通过的条件是**累计有效时长达到阈值**，而非最后上报的位置。

这解释了两个现象：

**现象 A：为什么失败后重跑要从 0 开始。**

`step6_video.py:169` 会先读一次状态，如果 `headOffset > 3` 但未通过，
就主动上报一次 `playingTime = 0` 把游标卷回去：

```python
if st and st['head'] > 3:
    self.report(job, dtoken, 0, isdrag=3)
```

不这样做的话，位置已经打满，循环条件 `while pt < dur` 直接不成立，
一个请求都不会发出去，永远补不上那部分缺失的时长。

**现象 B：为什么第一轮「全部白报」，第二轮却很快。**

第一轮 30 秒间隔的上报虽然没被计入有效时长，但请求本身是合法序列。
改到 60 秒后重跑，不少视频只跑到一半 `isPassed` 就翻转了 ——
说明服务端那边确实累积了一部分。

## 3. 限流的识别与自动降级

### 识别

限流的表征是**参数完全没变，但结果从成功突然变成全线失败**。

第二门课的实际轨迹：

```
前 5 个视频：2× / 3 路 / 60s 间隔  → 逐个通过
后 23 个：    相同参数                → 位置打满，全部未通过
```

同一份配置、同一门课、同一天，只有时间在变 —— 变量只能是服务端。

### 验证（这一步不能省）

不要凭猜测调参。做一个**单变量对照实验**：

```bash
# 取一个刚失败的视频，单独用更慢的速率跑
python step6_video.py <课程号> --kid <章节> --speed 1.5 --workers 1
```

实测结果：第三个上报周期就通过了。这排除了三种可能：
签名错误、`dtoken` 失效、任务点本身不可完成。**确认是速率相关的临时降额。**

### 降级

写进主循环，每轮结束检查：

```python
if ok[0] == 0:                                    # 这一轮一个都没过
    speed   = max(1.0, round(speed * 0.7, 2))     # 降速
    workers = max(1, workers - 1)                 # 减并发
```

降到 1.5× / 2 路后，剩余 23 个全部完成。

> 这里的判断逻辑值得说一下：**「成功数为 0」比「成功率低」更适合作为降级触发条件。**
> 因为限流是硬阈值，一旦触发就是一致性的全失败，不会只失败一部分。
> 如果只失败一两个，那更可能是网络抖动，重试就行，不该降级。

## 4. 答题侧：注入机制

### 4.1 为什么不装油猴

上游脚本是 UserScript，依赖 `GM_setValue` / `GM_xmlhttpRequest` / `GM_addStyle`
等 Tampermonkey 专属 API，外加 `unsafeWindow` 和 Sweetalert2。

装扩展的问题：多一步手动操作、版本会漂移、批量自动化时不好控制。

本项目的做法是把这些依赖**在页面里自己实现一遍**（`lib/xiaoai.py: POLYFILL`）：

| GM API | 替代实现 |
|---|---|
| `GM_setValue` / `GM_getValue` | `localStorage` |
| `GM_xmlhttpRequest` | `XMLHttpRequest` 包装（含跨域） |
| `GM_addStyle` | 动态插入 `<style>` |
| `GM_getResourceText('fontTable')` | 挂到 `window.__XA_FONT_TABLE__` |
| `unsafeWindow` | 指向 `window` 自身 |
| `Swal` | 直接 resolve 的 Promise 桩 |

然后把配置写进 `localStorage`（前缀 `GPTJsSetting.`），上游脚本启动时会自己读。

拼接顺序不能错：

```
jQuery → 字体表挂载 → 设置注入 → GM polyfill → 脚本本体
```

### 4.2 字体解密

超星把部分题干渲染成自定义字体。直接读 `innerText` 得到的是错乱的码位。

`assets/font_table.json` 是约 2 万条 `字体ID → 编码偏移` 的映射表，
上游脚本据此把码位还原成真实汉字。这份表是从真实页面采集的运行时数据，
不含任何个人信息。

### 4.3 穿透 iframe

答题页的结构是**主页面 → 任务点 iframe → 作业 iframe**，且层级不固定。

`step3_quiz.py` 用递归向下找，最多 5 层，用 URL 特征判断：

```javascript
if (/doHomeWork|selectWorkQuestion|\/api\/work/.test(href)) return iw;
```

**一个坑：不能用 `ananas/modules/work/index.html` 作为判断依据。**
那只是个空壳容器，真正的作业页在它的子级。按壳判断会拿到一个没有题目的窗口，
表现为「找到了 frame 但一道题都没有」。

另外，跨域 iframe 访问 `contentWindow.location.href` 会抛异常，必须 try/catch
包起来 —— 这也是为什么这个函数写成了递归 + 逐层 try。

## 5. 可检测性

这套东西不修改服务器数据，只是按照正常接口的格式发请求。但**这不等于不可发现**。

从平台侧看，以下信号是可用的：

| 信号 | 说明 |
|---|---|
| 上报时间间隔的规律性 | 人类的进度上报间隔有抖动（暂停、切标签、走神），脚本是精确的 60.0 秒 |
| `rt` 字段恒定 | 真实播放器的上报速率会有波动 |
| 同一账号的并发特征 | 多路同时上报不同任务点，人类不可能 |
| 昼夜连续性 | 连续 9 小时不间断推进 |
| 答题耗时分布 | 每道题固定 900ms 延迟，缺乏人类阅读时间的方差 |

**一个更现实的风险：`step3_quiz.py` 的答题延迟是固定的 900ms**（见
`delayFn: function () { return 900; }`）。如果一场测验的答题时间分布呈完美等距，
这在统计上一眼就能看出来。

如果要让它更像人，最少应该把延迟改成随机分布。`step3_quiz.py` 里还保留着固定值。

**本项目的定位是技术验证，不是规避审计。** 时序分布分析、行为指纹这类检测方法
在平台的公开风控材料里已有讨论，这套代码没有针对它们做任何对抗。

## 6. 复现方法论

如果接口或风控策略变了，这套代码会失效。重新摸出来的方法是固定的：

**① 抓真的。** 用浏览器正常播放一个短视频，在 DevTools Network 里过滤
`multimedia/log`，把完整请求的 URL 和参数抄下来。这是唯一的事实来源。

**② 对字段。** 拿抄下来的参数和脚本发的参数逐项比对。
签名是否一致，可以用同一个 `playingTime` 算两次 MD5 直接验证。

**③ 单变量实验。** 一次只改一个参数。改完观察 `isPassed` 是否翻转，
不要观察「是否报错」—— 这个接口的失败大多不报错。

**④ 记住这个接口的性格：**

> 不报错，不代表成功。
> 一切以 `isPassed` / `headOffset` 为准，不以 HTTP 状态码为准。

这也是 `step6_video.py --state` 存在的理由 ——
它不信任任何本地记录，每次都重新问服务端。
